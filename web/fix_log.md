## 第 10 轮 —— 「庇护作战」（大盾旗舰技能）实测恶化，已回滚

**知识库2 / 联网**：普鲁图斯之盾专属旗舰技能「**庇护作战**」—— 舰队**同时受到多支舰队攻击**时，所受「**作战主目标之外**」的其他来源伤害**减少 30%**。
（这也是你说的"拉格朗日_战报2 都有大盾的非主目标 30% 减伤"；实测确认**双方护航队都带大盾**：我方护航 ×1、敌方护航 ×4。）

**模拟器实测**：
- 库内给 `plutus-shield` 加 `fleetFlagship: {kind:'shieldProtect', cut:30}`；引擎在 `executeShot` 里按 `subTargetCount` 触发。
- **结果恶化**：时长 **+30.8% → +59.4%**、敌方护航对舰 **+48.7% → +118%**（通过项 9→9）。
- 原因：判定"非主目标来源"用的是"目标有没有还击 attacker" → **太宽松，双方互相减伤 → 互相打不动 → 战斗拖长**。

- 重做时要收紧到"**只有非主目标那一支**才减伤"（准备用 `_dByTF` 累计定义"作战主目标 = 该舰队输出最多的那支敌方舰队"）。

## 第 43 轮 —— ★ 全库武器「基础暴击率」（memory 实测依据）→ 保留

⇒ **暴击是【所有武器】的基础属性**，不是 24 门的特例。

⇒ **我不是"伤害量错"，是"速率错"——正好差「加点 + 暴击」那一块。**

`const critRate = 0.15 + (st.critRate||0)/100;`（原来是 `weapon.crit ? 0.15 : 0`）

**结果 5/18**：战报1 从 5/6 掉到 2/6（A 对空 +10.8%→**−19.3%**、B 对舰 −3.3%→**+20.6%**、B 维修 +1.9%→**+17.5%**）；

## 第 31~32 轮 —— 真因修正 + 一个战略性发现

### ① 修正我上一轮的判断：不是"117 个被当常驻"，而是"102 个已走条件触发、16 个掉回常驻"
引擎的条件触发管线是**完整的**：`buildAddPointBonus` 里只要 `BP_STATS.nodes[id].cond` 存在，
就 push 进 `conds`（不累加常数），由 `processCondEffects` 每 tick 按 条件 + 持续T + 冷却C 求值。
现有 125 个节点带 `cond`（`hpBelow`24 / `everySec`67 / `everyRounds`13 / `battleStartSec`10 / `battleStart`8 / `firstRounds`3）。

再扫那 117 个"限时"节点：**102 个已有 cond ✓**，**16 个没有**（因为它们的条件类型引擎还不支持）：

| 缺的 kind | 节点数 | 原文样例 |
|---|---|---|
| `onAttacked`（受到攻击/战机打击时触发） | 9 | 「受战机攻击时，系统内武器冷却下降 30%，持续 T 秒，冷却 C 秒」 |
| `onTargetType`（目标为某类舰船时） | 2 | 「目标为巡洋舰时，伤害提升 60%…」 |
| `onKill`（消灭目标后） | 1 | 「本舰船武器消灭目标后…」 |
| `onEnemyLoss`（对方损失舰船时） | 1 | **「对方损失舰船巡洋舰时，系统内武器冷却时间下降 85%，持续 10 秒」← 就是太阳鲸那个** |

⇒ **`condWants` 的 `default: return true` 让这 16 个"永不满足条件"的节点变成了"永远满足" → 常驻。**
这才是太阳鲸超发 10 倍（`BG-2450A` 513s 打 13,150 发 vs 应有 1,221 发）的真因。

### ② ★ 停用这 16 个 → **9/18（−1），已回滚**；但它暴露了一个更重要的东西

| 指标 | 停用前 | 停用后 |
|---|---|---|
| **战报2 时长** | +31.4% | **+74.2%** ❌ |
| 我方被护航 对舰 | +14.5% ✅ | +61.2% ❌ |
| 敌方护航 生存 | 55.5% | 66.5% ❌ 更差 |
| **通过项** | **10/18** | **9/18** |

**⇒ 意思是：我现在的 10/18 是"靠太阳鲸超发(10倍)撑着"的。**
把那个 bug 修掉，战斗立刻从 511s 涨到 678s（游戏 389s）。

### ③ 战略性结论（这是本轮最值钱的东西）
**我的模拟器存在"系统性偏慢"，而所有"减少输出 / 增加硬度"的**正确修正**都会加剧它：**

| 修正 | 是否属实 | 时长结果 |
|---|---|---|
| 庇护作战（大盾非主目标减伤）×3 | ✅ 真实机制 | +59% / +67% / +19% |
| 航母护甲 15→270（数据错误修复） | ✅ 有资料 | +31% |
| 117/16 个限时节点不再当常驻 | ✅ 属实 | +80% / +74% |

**⇒ 每一项单独看都是"把错的改对"，但合起来方向一致地把战斗拉长 —— 说明我缺一个"让战斗更快"的真实机制。**

**而我一直卡在一个算术矛盾上：游戏战报2 里"我方全灭(0/695)"，可敌方两页的对舰伤害只有 359+56 = 415万，

1. **游戏里"我方总血"远小于 997万**（即我某些舰船的血量数据偏高）；
2. **或"对舰伤害"那一列不含【系统伤害】，而系统伤害(击毁系统扣5%船血)才是打死我方的主力** ——

**下一轮：先定死这个矛盾**（对比"战报里我方承受的伤害"与"我方总血+维修"），

## 第 29~30 轮 —— ★★ 抓到超发根因 + 发现 117 个「限时」节点被当常驻（禁用会恶化，已回滚）

### ① 超发根因：把【条件触发+限时】的加点当成了【常驻】
插桩数 `BG-2450A双联重型火炮` 的实际发射次数：**513 秒打了 13,150 发**，
而按"每轮 2 发、冷却 4.2s"应为 **1,221 发** —— **超发 10.8 倍**（折算 5.13 发/秒/艘 vs 应有 0.476）。

顺藤摸到太阳鲸加点 **801010309「工作效率提高」**：
> 原文：**「对方损失舰船巡洋舰时，系统内武器冷却时间下降 {101}%，持续 {T} 秒。」**（85% / 10 秒）
> `levelValue = [["0","0"],["85","10"]]`

**这是"对方损失巡洋舰时触发、只持续 10 秒"的效果，引擎却把它当成了【常驻冷却缩减 85%】**
→ 太阳鲸武器几乎无冷却开火 → 超发 10 倍（`cooldownReduction` 合计被算成 96.2%，被 `Math.min(95,…)` 截断）。

### ② 全库扫描：**117 个可加点节点的原文是「限时/周期」，却被当常驻消费**
| stat | 数量 | 典型原文 |
|---|---|---|
| hitBonus | 47 | 「战斗开始后，敌方对自身的攻击命中率额外下降 X%，**持续 T 秒**」 |
| cooldownReduction | 35 | 「**受到对方战机打击时**，系统内武器冷却时间下降 X%，持续 T 秒，冷却 C 秒」 |
| evasion | 21 | 「**每 P 秒**启动干扰系统，闪避率提升 X%，持续 T 秒」 |
| repairEff / weaponDuration / crit / 其他 | 14 | 「**每 P 秒**…持续 T 秒」 |

⇒ **这解释了「敌方两支队的对舰都偏高 90%~158%」—— 双方火力被系统性高估。**

### ③ 尝试"直接禁用" → **8/18（−2），已回滚**
把这 117 个节点的 `stat` 改成引擎不认识的 `timedPending`（原名存 `_origStat`）后：

| 指标 | 改前 | 改后 |
|---|---|---|
| 战报1（5/6） | 5/6 | 5/6（未变）|
| **战报2 时长** | +31.4% | **+80.3%** ❌ |
| 我方被护航 对舰 | +14.5% ✅ | +69.8% ❌ |
| 敌方护航 生存 | 55.5% | 69.1% ❌ 更差 |

⇒ **禁用等于"这些加点白点了"**，双方输出一起掉、战斗大幅拉长。**通过项优先，已回滚到 10/18。**

### ④ 正确解法（下一轮）
这 117 个必须走引擎已有的 **`condEffects`（条件触发）** 路径 —— **按条件触发、按 T 秒限时、按 C 秒冷却**，
而不是"常驻"或"禁用"。引擎里 `processCondEffects` 已存在（memory 记着"条件触发 119 个已实现"），
这 117 个是**漏网的同一类**。需要：`_build_bpstats.js` 的 conds 识别规则放宽 + 把 `levelValue` 的
`[值, 持续时间]` 按占位符顺序解析。

# 第63轮（2026-10-02）修战报弹窗「点不动 / 开不了别的船」——两个真 bug

用户报：**「战报跳出来后我无法移动点击战报里的所有东西；以前点开一条舰船详情后，就再打不开其它舰船的详细数据了。」**
写了 `test/battle_report_modal.js`（**15/15**，全部用真实鼠标点击 + `elementFromPoint` 判"是否被挡住"），定位到**两个独立 bug**：

## bug 1：`bsdOpen` 漏加 `active` 类 → 弹窗**全屏透明但拦截所有点击**
- CSS 里 `opacity:1` 挂在 `.modal-overlay.active` 上；HTML 又写了行内 `style="display:none;"`。
- 原 `bsdOpen` 只做 `m.style.display='flex'` → 遮罩变成 **`position:fixed` 铺满全屏、z-index 2000、opacity 0** 的一层，
  **看不见但吃掉所有点击与滚轮** → "点一次详情之后什么都点不动"。
- 修：去掉行内 `display:none`；`bsdOpen` 改走 `openModal('bsdModal')`；关闭改走 `closeModal`；
  另加「← 返回战报」按钮 + **点遮罩空白处关闭** + ✕（三种关法，实测都可）。
- 全库排查：这种"直接 set display=flex"漏 active 的写法**只有 bsdModal 这一处**（已 grep 确认）。

## bug 2（更隐蔽）：战报每行的 `<div>` **从来没闭合** → 行行嵌套 → 点第 N 行会被第 1 行抢走
- `_statTable()` 里每行以 `<div ... onclick="bsdOpen(...)">` 开头，**到行尾没有 `</div>`**
  → 浏览器把后续每一行都解析成**上一行的子节点**（行 1 ⊃ 行 2 ⊃ 行 3 …）。
- 后果：点第 2 行时事件从内往外一路冒泡，**最外层（第 1 行）的 onclick 最后执行**，
  所以 `SD.key` 永远被改回第一条船 → 正是用户说的"开不了别的船的详细数据"。
- 定位过程（都留了证据）：先用「包装 bsdOpen 记录调用栈」看到**一次点击触发两次 bsdOpen**（红宝石 → 又回愤怒），
  再用 `document.addEventListener('click', …, true)` 证明**只有一个真实 click 事件**（isTrusted=true）
  → 推断是嵌套冒泡；最后 `row.querySelector('div[onclick^=bsdOpen]')` 计数 = 3 行嵌套证实。
- 修：行尾补 `'</div>'`；详情行作为兄弟节点跟在后面。
- 回归断言（防复发）：**"战报行互不嵌套（嵌套行数=0）"** + **"战报里的按钮全部可点（5 个）"** + **"战报可滚动"**。

# 第66轮（2026-10-02）★ 修用户报的真 bug：护航打到一半"跨过护航舰队直接打两个舰队"

## 症状与复现
用户原话：「4 个舰队都有的情况下，打了一半、4 支舰队都还在，突然 A 方可以同时对 B 方的 2 个舰队同时攻击」。
写了 `_probe_escort_bug.js`（浏览器里**逐 tick 采样**，判定两条）：
① 任一单位的目标里同时出现敌方【两支舰队的舰船】→ dualTarget
② 被护航队的舰船在本方护航队存活时掉血 → escortBreach
**修复前实测：dualTarget = 12 次**（t=0.2s 起：普鲁图斯之盾、天枢级航母、ST59…每次都有），escortBreach = 0。

## 根因（代码级）
`escortProtected()` 被写成了 **`return false; // ★ 不再隔离被护航队`**——
即"护航免疫"只剩 `executeShot` 里"伤害清零"那一半，**目标选择层的隔离被彻底关掉**。
后果：目标照样被选上、炮照样开、只是伤害 0 ⇒ 界面上就是用户看到的"同时对两个舰队开火"。

## 修法

# 第68轮（2026-10-02）诊断：「敌方护航生存 41% vs 86%」坐在悬崖上（重新定性）

## 实测数据

## 结论（重新定性，很重要）
1. **这不是"差 6.6 倍"的模型错**，而是**总量坐在悬崖上**：总血 413万，游戏打 395.9万（**低于**总血 → 几乎不死），我打 466万（**高于**总血 → 全灭）。
   **13% 的伤害差 → 从 86% 存活翻到 0% 存活**。所以「敌方护航 生存占比」这个指标**极度敏感**，不能当主要标定靶。
2. 同轮验证：把分摊从 `floor(n/2.5)` 改成"铺开到全部目标"→ 死得**更多**（35/35）——因为总量超了总血，怎么分都要死。
   **分摊口径不是这个指标的杠杆**（实验已回滚）。
3. 真正该做的是把"我方对敌护航的伤害"从 466万 压到 ~396万（**−15%**），而这与我方整体输出偏低（B 对舰 −7.8%、B 对空 −19.3%）**方向相反**

# 第72轮 · 七补记（同日）：★按《战斗机制》重写【系统伤害】为「命中分流」模型（用户指认 + 知识库原文）——用户场景摧毁系统 0→4 个，验收回到 13/18

### ① 知识库权威原文（此前一直没找到的那段，这次找到了）
`知识库2/知识库/战斗机制.md` §195-203 + §363-378「结论先看」：
- 「系统伤害效率高中低指的是**命中分流比率**，高中低比率分别是 **60%、40%、20%**」〔§369〕
- 「武器发射后，会先被对方闪避、拦截，**剩下的伤害**还要看对目标系统的效率高低」〔§199〕

  （≈ 分流 60% × 系统攻击系数 1.25~1.5 = 75%~90%，与 §369/§373 自洽）

### ② 旧实现错在哪（形状就错了，不只是数值）
旧＝"概率小口啃"：每轮期望=效率值的**判定** + `单发×1.5×暴击` 的**独立小伤**。
正确＝**每发命中都分流**：`系统部分 =（单发+加成）×调校×暴击 × 分流比率(60/40/20%) × 系统系数(默认1.5)`，**全额、不吃护甲**；
`结构部分 = 原公式 × (1−分流比率) × 结构系数`，照常吃抗性伤。
（死键修复、skip 已毁系统修复、复活回血修复都保留；`SYS_JUDGE_MUL` 概率倍率**已删除**。）

1. 伤害计算前：按 `subSystemTargets` 键序找第一个名字/类别匹配且未毁的系统 → `_sysSplit={sys,ratio}`；常量 `SYS_SPLIT={high:.6,medium:.4,low:.2}`、`SYS_ATK_COEF=1.5`、`STRUCT_COEF=1.0`；
2. 物理/能量分支：结构侧乘 `(1−ratio)×STRUCT_COEF`（含 10% 保底口径）；
